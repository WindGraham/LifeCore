# 主动外伸层 · 设备/连接目录与"核心能主动伸手"

> 2026-09-17 · docs/13 综合方案的第 3.5 章（新轴：核心能主动建立服务）
> 一句话：把 LifeCore 从"边缘推数据"升级为"核心能主动伸手"。三层（设备 / 能力 / 远端服务句柄）+ 通道复用 + 红线三件套。

## 0. 与综合方案（docs/13）的衔接

docs/13 的 §3 写的是"核心智能化（被动响应 + 主动行为）"。本章加一个**被之前漏掉的能力前提**：核心要主动，得先**知道它能联系谁、怎么联系、联系之后能做什么**——这是设备/连接目录。同时核心要主动地**在远方起一个服务**（自建 webhook、本地 MCP、ad-hoc 隧道），这是"主动外伸"。这两件事一起决定 P3 之后 LifeCore 的天花板。

与 docs/13 的关系：
- §2 信条（沉默观察）= 默认姿态；本章 = 在姿态保持之下"能伸手就伸手"的兜底能力
- §4 主动行为 B7（跨通道主题收敛）依赖本章"目录查得到"作为前置
- §6 落地分期的 P2+ 自动包含本章的 P0/P1 实施

## 1. 三张表（职责清晰分离）

不复用 `device_token`——那是**认证凭据**，不是设备描述。把它当外键引用即可。

### 1.1 `devices` —— 设备台账（人/事层面，慢变）

| 字段 | 类型 | 来源 | 备注 |
|---|---|---|---|
| `device_id` | TEXT PK | 声明 | 人类可读，如 `pixel-chenxi`、`pc-home`、`vps-hermes` |
| `device_type` | ENUM | 声明 | `vps / pc / android / ios / cloud-saas / iot` |
| `display_name` | TEXT | 声明 | "陈西的 Pixel 8" |
| `owner_user_id` | TEXT FK | 声明 | 多用户预留（当前=1） |
| `default_channels` | JSON | 声明 | `["ws", "adb", "ssh"]` 候选，按优先级 |
| `active_channels` | JSON | **探测** | 当前实际通的，TTL=60s |
| `last_seen_at` | REAL | 探测 | |
| `last_health` | TEXT | 探测 | `ok/degraded/down/unknown` |
| `tags` | JSON | 学习 | `["home_only", "low_battery_often"]` |
| `created_at` / `updated_at` | REAL | 系统 | |

**变化节奏**：声明字段几乎不动；探测字段高频；`tags` 慢慢累积。

### 1.2 `device_capabilities` —— "这台机器能被我指挥做什么"

| 字段 | 类型 | 备注 |
|---|---|---|
| `cap_id` | TEXT PK | `pixel.gws_read_mail`、`vps.spawn_webhook`、`pc.adb_shell` |
| `device_id` | TEXT FK | |
| `cap_kind` | ENUM | `read / write / exec / spawn / expose` |
| `risk_class` | ENUM | `R0_readonly / R1_local_mutation / R2_external_visible / R3_destructive` |
| `requires_grant` | BOOL | 是否要一次性用户授权 |
| `granted_at` | REAL | 授权时间（一次性） |
| `last_probed_at` | REAL | |
| `last_probe_ok` | BOOL | |
| `cost_hint` | JSON | `{battery, network, user_visibility}` |
| `enabled` | BOOL | 临时关停（kill switch 入口） |

### 1.3 `remote_services` —— "我刚在这台机器上拉起的活服务"（短命，分钟-小时级）

| 字段 | 类型 | 备注 |
|---|---|---|
| `service_id` | TEXT PK | UUID |
| `device_id` | TEXT FK | 跑在哪台 |
| `kind` | ENUM | `local_mcp / webhook_endpoint / tunnel / ssh_reverse / adbd_session` |
| `endpoint` | TEXT | 核心视角的地址 |
| `protocol` | TEXT | `http/mcp-v1/grpc/...` |
| `auth_ref` | TEXT FK→`device_token` | 复用凭据体系 |
| `channel_ref` | TEXT | 用了哪条通道（frp/ssh-reverse/...） |
| `spawned_at` / `expires_at` / `last_heartbeat` | REAL | 全部带 TTL |
| `purpose` | TEXT | 事后审计用 |
| `rollback_cmd` | TEXT | 关闭脚本/命令（必须填） |
| `state` | ENUM | `pending/active/expired/killed` |

**关键纪律**：`remote_services` 不像设备表那么长寿。Hermes 不改 → 这张表落在 lifecore-server 同库 SQLite，配 `/internal/services` 管理端点给边缘 agent 拉自己的"待启动清单"。

### 1.4 三类字段切分
- **声明**：用户元数据 / 静态配置
- **探测**：核心主动或边缘自报（高频）
- **学习**：`tags/cost_hint` → `user_model/<device>.json`，30 天聚合一次

## 2. 四种典型"主动建立服务"场景

### 场景 A · adb wireless 拨号拉通知
- **触发**：Pixel WS 断了 60s + 上次 `adb-over-wifi` 健康过
- **能力边界**：只读 + 有限写（拉通知列表、清单一写不存存）；**禁止 `pm install` / `am force-stop` / 改系统设置**
- **回滚**：`adb disconnect <ip>:5555`，记录 `service_id` 销毁
- **通道**：frp stcp 把 Pixel `5555` 暴露到 VPS 本地端口；核心连 `127.0.0.1:<port>` 即可

### 场景 B · 在 Pixel 上自部署轻量 MCP（通知/截屏/位置/电池）
- **触发**：B7 跨通道主题收敛命中 Pixel 端能力；或长任务超过 WS 超时
- **能力边界**：每工具单独 `cap_id` + `risk_class`；新增工具必走"宣告-等待-启用"三步
- **回滚**：`adb shell am force-stop com.lifecore.mobile.mcp` + 关 frp 映射
- **通道**：frp stcp 复用 + HTTP MCP，不需要为 MCP 起新隧道

### 场景 C · 在 VPS 自己开临时 webhook 收 SaaS 推送
- **触发**：用户配置某个 SaaS 时（"通知我 Lifecore"）
- **能力边界**：只允许 HTTPS POST 接收；HMAC 验签；白名单路径 `/wh/<uuid>`
- **回滚**：撤路由 + 删 `service_id`；URL 一旦用过一次后缀立即换
- **通道**：直接 VPS 公网 443 路径前缀，**不走 frp**（VPS 本身就是公网入口）

### 场景 D · google-bridge 暴露 MCP 给核心调
- **触发**：核心要做 Gmail/Calendar 操作但 WS 没回包；或用户明确说"用 gws 帮我..."
- **能力边界**：开 = `R1_local_mutation`（发邮件、建事件），禁 = `R3_destructive`
- **回滚**：google-bridge 本地关闭 MCP server 端口
- **通道**：复用现有 google-bridge → Hermes 通道（HMAC），在 Hermes 侧加 `x-lifecore-mcp-route: google` 头路由

## 3. NAT 穿透与可达性（个人系统级别，4-6 台）

| 通道 | 适用 | 复用性 | 出新端口成本 | 评分 |
|---|---|---|---|---|
| **frp stcp**（已有） | 同账号设备互访 | ★★★ 同一通道换端口 | 改 frpc.toml 加一行 + 重启 frpc | **首选** |
| **Cloudflare Tunnel** | VPS ↔ SaaS，无 NAT | ★★ | 0（VPS 装 cloudflared） | 场景 C 备选 |
| **Tailscale Funnel** | Pixel/PC → 公网暴露 | ★★ | 需要设备装 Tailscale | 应急 |
| **SSH 反向 `-R`** | 一次性 ad-hoc | ★ | 每条单独建 | 回退 |
| **手动端口转发** | 用户在场时 | 0 | 人肉 | 永远兜底 |

**关键判断**：**不要为每个服务起新隧道**——frp stcp 已有，新需求只是 `device_id` 表里加一行 `remote_services`，frp 配置热加载（不用重启 frpc）。**通道 = 设备级，不 = 服务级**（一个 Pixel 一个 stcp 通道；它后面挂了 N 个 MCP 工具都是不同本地端口）。Hermes 不知道通道细节——通道细节在 lifecore-server 的 `remote_services` 表里；Hermes 仍只看到一个"内部路由"。

### 主动暴露新服务 SOP
1. 核心查 `device_id.capabilities` 确认能力存在且 `enabled=true`
2. 写一条 `remote_services` 行 `state=pending`
3. 通过 frp 控制端点（VPS 127.0.0.1:7500 HTTP API）加路由
4. 在 Pixel/PC 上触发 `adb shell am start-foreground-service` 或 `systemd-run` 启服务
5. 探测端点 200 OK → `state=active`，TTL 计时开始
6. 到期或 kill → 调 `rollback_cmd` → `state=killed`，frp 路由回收

## 4. 核心"知道它能做什么"——mix 策略

| 来源 | 占比 | 时机 |
|---|---|---|
| **用户元数据** | 60% | `lifecore init` 时一次性扫描；UI 里"我的设备"页可改 |
| **自动探测** | 30% | 每次"想用之前"跑一次无副作用探针：`gws users get profile` / `adb shell getprop ro.build.version` / `mcp/list-tools` |
| **学习** | 10% | 30 天滚动窗口写入 `user_model/<device>.json`：`used_capabilities[]`、`failed_recently[]`、`cost_observed` |

**判断**：**学习权重低、探测权重大**——个人系统设备少，样本不足以"学习"，更可能是噪声；探测一次成本低、信号准。能力表 `last_probe_ok` > 24h → 下次使用前强制重测。

## 5. 安全边界（红线/灰区/绿区）

### 红线（永远不允许，即便用户授权）
- 装/卸 APK（`pm install`）
- 改系统分区、刷机、bootloader 解锁相关
- 撤 OAuth token、删账号、删邮件
- 任何 `R3_destructive` 类操作
- 核心直接拿键盘/鼠标控制设备 UI（除非显式"演示"模式 + 60s 自动断）

### 灰区（一次性显式授权，落 `granted_at`）
- 暴露新 MCP 工具
- 在用户设备上起长驻服务 > 1 小时
- 任何带外部可见副作用的（场景 C 的 webhook 公开 URL）
- 跨设备转发用户数据

### 绿区（默认开放，登记即可）
- `gws` 读操作（读邮件、读日历、读联系人）
- IMAP/IMAPS 拉邮件
- `adb` 只读类（`dumpsys` / `logcat -d` / 截屏）
- VPS 本地 webhook 收自己 declare 的端点
- 设备心跳、ping 类探测

### Kill switch（紧急撤权）
- `device_capabilities.enabled=false` → 立即生效，所有 `cap_id` 下次使用被拒
- `remote_services` 行 `state=killed` + 通道回滚（关 frp 路由、杀进程、删 webhook）
- 用户在 Web UI 一键"停用全部主动连接"（设备级 bulk kill，对应 `devices.tags` 加 `"emergency_disabled_until"`）
- 落地一条 `feedback_events` 记录原因

## 7. 实施路线 P0–P2

### P0 · 最小骨架（1-2 天）
- 加表 `devices / device_capabilities / remote_services`（单库迁移）
- `device_token` 表加 `device_id` 列（nullable，向后兼容）
- seed 三台：vps / pc / pixel
- 边缘 agent（google-bridge、pixel-android）**只加心跳上报 `last_seen_at/active_channels`**，不动 Hermes
- Hermes **零改动**

### P1 · 主动通道 + 单设备 MCP（3-5 天）
- 实现 SOP：写 `remote_services(pending)` → 调 frp 控制 API → 启服务 → `active`
- 场景 A（adb 拨号）跑通：触发、TTL、回滚
- google-bridge 暴露 MCP 一组只读工具（场景 D 的 R0/R1）
- `device_capabilities` 填齐当前真实能力
- 加 `/internal/services` 端点：CRUD + kill

### P2 · 多服务并行 + 学习层（3-5 天）
- frp 配置热加载
- 场景 B（Pixel 端 MCP）跑通——挑 2 个工具：通知拉取 + 截屏
- 场景 C（VPS webhook）跑通
- `user_model/<device>.json` 接入：`used_capabilities / failed_recently`
- Web UI 加"我的设备/主动连接"页 + kill switch 按钮
- 7 条触发器升级：B1/B2/B5 加 `devices.health` 前置，B7 切到目录驱动

### P3+ · **不该做**（敢说清）
- ❌ 跨用户/跨账号设备共享（个人系统）
- ❌ 自动设备发现协议（人太少，手工登记更准）
- ❌ 自动 OTA 升级（核心不应能改边缘代码版本）
- ❌ 服务网格 / mTLS 大平台化（frp + device_token HMAC 已经够了）
- ❌ 把 `remote_services` 落 Hermes（保持 Hermes 通道透明）
- ❌ 让核心自己跑 SSH 客户端到边缘（一旦持有 SSH 凭据红线守不住；永远"边缘暴露、本地调用"）
- ❌ 把"主动建立服务"暴露给通用规划路径（必须显式触发：用户词、通道超时回退、B7/B8）
- ❌ `device_capabilities` 做成字符串白名单——`cap_kind + risk_class` 枚举才是边界，字符串粒度会漏
