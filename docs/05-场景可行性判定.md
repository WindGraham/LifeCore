# 场景可行性判定（2026-09-16 场景压测）

> 方法：九个真实场景逐条对照 Hermes 六个官方扩展面（webhook / MCP client / mcp serve / hooks / api_server / state.db 只读）+ 外围三件套（registrar / inbox / list_manager）判定。
> 等级：① Hermes 现成 → ② 纯配置 → ③ 外围薄壳 → ④ 真自研 → ⑤ 物理不可行。

## 总判定

**九个场景无一需要修改 VPS 的 Hermes 核心，无④无⑤级。** 分布：场景 2/3/6 ≈ ①；场景 1/5 ≈ ②③；场景 4/7/8/9 ≈ ③（落在外围件）。

## 逐场景判定

### 前导：核心 agent 直接交互 + TTS + App 可回复
Hermes 网关标准形态（发消息/收回复），客户端换成自有 App（docs/01 既定差异化）。回复管道 = App 上行 webhook / api_server。回复的人性化设计待专项讨论。

### 场景 1：微信 root 监控（已修订为四层架构，见 §13 与 contracts/edge-agent.md）
- 原文全量存档在地方（DB 本来就在），**VPS 不存全量明文**；
- **地方常驻摘要 agent**（vendor harness，带记忆）持续处理微信流，只上报有效信息摘要 + 精确指针；
- 核心需要原文 → MCP tool 按需回查；
- 指派回复群聊 = 微信 Skill 包成 MCP server，核心经 MCP client 调用；不可逆动作走 exec approval；
- 合规：自用等级（root 自己设备自己号）；敏感群可配置"只上元数据"，B/C 级永不离开地方。
- 等级：③（值守脚本 + MEMORY.md 规范 + 回查 MCP 是自研件；VPS 核心零修改）。

### 场景 2：定时任务程序（双向）
地方定时程序 = MCP server（add/update/list_reminders）+ 到期 POST webhook；谷歌日历/邮箱 = 官方 MCP server。"晚点再提醒我" = agent 调 tool 改时间 → 到点 webhook 触发 → deliver 通知。等级：①②。

### 场景 3：长时间巡查
Hermes cron 原生为此设计：agent 用 `cronjob` 工具自建"每 2h 巡查"任务，持久化、跨重启、到点 deliver、获知后可取消。地方巡查 = 场景 2 模式。需设计的是 prompt 工程（何时宣布无结果、频率衰减控成本）。等级：①。

### 场景 4：程序 agent 自主设计汇报（agent.md 旗舰场景）
程序侧 agent 读 contracts/agent.md → 注册通道 → 自设触发/结束条件 → 自测。agent.md 需含《汇报设计规范》节（触发/结束/自删除语义，已写入）。等级：③（registrar）。

### 场景 5：地方作业 agent + 记忆
指派 = 任务单（goal/context/callback=webhook），通道 A2A（Hermes 有 a2a 插件）或 MCP tool。"无头模式无记忆"解法 = 常驻 runtime + 会话 resume + 外置记忆文件（见 contracts/edge-agent.md）。等级：②③。

### 场景 6：缓存便宜
Hermes 强项：per-conversation prompt caching 是 sacred invariant，另有 micro-compaction / trajectory 压缩 / 上下文压缩。等级：①。

### 场景 7：地方日志规范 + 核心远程搜索
规范 = agent.md 接入契约条款（注册时强制声明日志位置/保留期）；远程搜索 = 地方暴露 `search_logs` MCP tool 或 SSH terminal backend。等级：②③。

### 场景 8：并发 + 信息氛围 + 多个 list
- **list 们不进 prompt**（污染+炸缓存）；形态 = **list_manager MCP server**（带时间戳读写、schema 校验、单行摘要+详情指针约束）；
- "接入服务清单" = registrar 注册表的投影，注册时强制填写设备/程序/用途/状态，自动生成；
- 消息时间戳注入 = Hermes 原生 `message_timestamps`；
- agent 可编辑/频繁读写 = MCP tool 天然权限边界。等级：③（list_manager ≈500 行自研）。

### 场景 9：并发模型（快照起新 agent / tree 分叉复用缓存 / 分叉又汇总）
- 每会话独立 agent、会话间并行、会话内串行（turn lease 已验证）✅；
- 缓存复用：同 system prompt 头部 → provider 侧缓存命中 ✅；
- **"分叉又汇总" = 共享状态而非共享上下文**：分支会话结束把结论写回 list_manager，主干从 list 读——比 DAG 上下文拼接便宜一个量级且可审计；
- 待验证项（构造分析）：`/btw`、`/rollback`（checkpoint）、bg 会话三者的上下文关系——可能是 tree 的现成雏形。

## 收敛：五条设计原则

1. **数据主权**：VPS 只存元数据+短摘要+指针；原文留地方，经 MCP tool 按需拉取；可选加密副本兜底多设备（VPS 存密文不可读）。
2. **四级分级**（修订版）：地方过滤器 → **地方摘要 agent（带记忆，高容量源）** → 核心裁决 → 动作。"智能集中"重新表述为**裁决集中**：打扰裁决与全局汇总必须在 VPS，预处理属于边缘。
3. **状态服务化**：一切 list = MCP tools，不写死 prompt；易变状态工具优先，瞬时注入兜底（注当前回合末尾，永不落历史）。
4. **汇总靠共享状态，不靠共享上下文**（DAG 的便宜替代）。
5. **指派 = 任务单**（goal/context/callback=webhook）+ approval 守门不可逆动作。

## 战略记录

用户偏好：不喜欢 Hermes；地方能力 agent 用 vendor harness（Kimi Code headless / DeepSeek harness / Claude Code 等以能力为目标的 harness）。Hermes 仅因网关价值留在 VPS 核心位置；**边缘 agent 只经标准表面对话（webhook 上行 + MCP 下行），对 VPS 内部无感**——保证核心将来可整体替换为 vendor harness 而边缘零改动。
