## 0. 文档目的

记录"个人聚合 Agent 系统"的完整调研过程与最终架构设计，覆盖：

1. 需求从何而来（场景与约束）；
2. 开源生态调研结果（协议、网关候选、参考项目）；
3. 每个架构决策的理由与备选方案；
4. 可执行的部署方案与落地路线。

阅读对象：本系统的唯一开发者（兼唯一用户）。

## 1. 愿景与需求

### 1.1 场景描述

用户佩戴耳机或智能眼镜，手机上运行一个 App。系统的核心是一个**网关**，持续聚合接收各种来源的信息：微信消息、微信群聊、课程通知、工作安排、天气、日历更新、最新新闻、电话短信、工作待办、某台电脑上的 agent 任务完成等。

一个**核心 Agent** 不断接收这些信息，汇总、整理、判断重要性，将值得知道的结果通过语音反馈给用户（经由耳机）。

同时，用户可以通过语音要求系统**对某条信息采取行动**，例如："把这条消息回复掉""帮我把电脑上那个报告整理一下"。

### 1.2 功能性需求

**入向（信息聚合）**：接入至少以下源头——

| 源头 | 性质 | 接入难点 |
|---|---|---|
| 封闭 IM（微信等）——**产品不接入** | 无官方个人号 API | 消息经通知监听在系统层只读捕获；回复引导至开放协议 IM |
| 手机通知（课程 App、短信、任何无 API 的 App） | 系统级 | 需 NotificationListenerService 兜底 |
| 日历（课程/工作安排） | 第三方 API | 有现成 MCP server |
| 天气 / 新闻 | 轮询型 API / RSS | 简单 |
| 工作待办 | 视具体系统 | 多数有 API 或 MCP server |
| 电脑 agent 任务完成回报 | 自研 webhook | 零难度 |

**立场（2026-09-15 定）**：本产品对微信零集成——不做扫码授权、不调用任何微信接口。微信消息到达时系统通知栏可见的内容由通知监听只读捕获（与所有 App 一视同仁）；需要双向 IM 动作的用户，引导使用开放协议平台（Telegram / Matrix / Slack 等，均有官方 bot API）。

**出向（动作分发）**，用户明确提出的三个例子：

1. **返回到一台设备上的 agent 执行**：该 agent 可能有固定工作目录、可能有整机权限、可能带记忆、可能是 Kimi Code 无头模式常驻——形态多样；
2. **返回到一个特定的庞大定制程序**：程序本身繁琐、高度定制、只完成特定任务；
3. **接入第三方服务**：如谷歌日历。

**交互方式**：语音进（耳机麦克风）、语音出（TTS 到耳机）；异步任务完成后的主动播报。

### 1.3 非功能性需求（用户提出的七条标准 + 两条硬约束）

七条标准：**自己配置、原理优雅、性能高、开销低、持续运行、兼容性强、可接收各种不同源头信息。**

两条硬约束：

1. **可穿戴设备**：至少能长时间佩戴并听见的设备（耳机/眼镜）；
2. **App 不被杀后台**：需要白名单机制，或者即使被杀也能继续接收信息（"多模态 token"）。

### 1.4 本质判断

这个需求**不是**一个 API 网关（APISIX/Kong 那类"请求代理"），而更接近一个 **个人事件总线 + 核心 Agent + 动作分发层** 的三位一体。在开源生态中没有单一成品能直接充当它，但每一层都有成熟组件，拼起来正好是目标架构。

关键时间点：2025–2026 年出现的两个协议（MCP、A2A）和一个事件标准（CloudEvents）恰好把"各种不同源头"与"各种不同动作目标"两大难题标准化了——这是本方案"原理优雅"的根源。

### 1.5 产品信条（2026-09-15 定，后续所有设计决策的裁判标准）

1. **自有 App 是产品本体**：不寄生在第三方聊天 App 里（区别于 OpenClaw/Hermes 的路线）。通知监听、耳机音频管道、事件收件箱是不可让渡的差异层；
2. **零私有协议——我们只是把已有的网络协议配置起来**：一行基础协议都不发明；系统每个能力都可指认到具体协议的具体特性；UI 中明示协议链路；文档致谢所有上游生态。**"本产品零私有协议"是卖点而非弱点**：每一层都是标准件，用户可随时拆换，无锁定；
3. **配置双层目标：极易用 × 极开放**。分层配置模型：L0 模板（一键）/ L1 表单（JSON Schema 渲染）/ L2 文本（manifest 原文编辑）/ L3 逃生舱（自带 MCP server 填 URL、自挂 webhook、Node-RED sidecar、SSH）。L0–L2 是同一 manifest 的不同视图；L3 的完全开放性由标准协议白送——不需要"提供扩展 API"。

## 2. 关键协议与标准（调研结果）

### 2.1 MCP（Model Context Protocol）

**是什么**：Anthropic 于 2024 年底开源的连接协议，回答一个问题：AI 应用如何统一地访问外部数据和工具。类比：数据源以前像各种专用充电线，MCP 要做的是 **USB-C 接口**。2025 年起 OpenAI、谷歌等各家宣布支持，现已是事实标准。

**三个角色**：

```
┌─────────┐     ┌────────┐     ┌──────────┐
│  Host    │ ←→ │ Client │ ←→ │  Server  │
│ (AI应用) │     │(连接器)│     │(能力提供方)│
└─────────┘     └────────┘     └──────────┘
 Claude Desktop   每个 server    谷歌日历 MCP
 Kimi Code        配一个 client  数据库 MCP
 你的核心 agent                  IM bot MCP
```

- **Server**：能力提供方；
- **Client**：嵌在 AI 应用里，连接某个 server（client 从不单独部署，跟着宿主走）；
- **Host**：AI 应用本身，可挂多个 client。

**Server 提供的三种原语**：

| 原语 | 是什么 | 例子 | 谁触发 |
|---|---|---|---|
| Tools（工具） | 可执行函数（动作） | 发送消息、创建日历事件 | LLM 自主决定调用 |
| Resources（资源） | 可读取的数据（上下文） | 文件、数据库记录、网页 | 应用/用户 |
| Prompts（提示模板） | 预设提示词工作流 | "总结文档并提取待办" | 用户 |

一个 Tool 的定义示例：

```json
{
  "name": "create_calendar_event",
  "description": "在谷歌日历中创建一个新事件",
  "inputSchema": { "title": "string", "start": "datetime", "end": "datetime" }
}
```

LLM 看到的就是"名字 + 人话描述 + 参数格式"的清单，想调用就发 JSON-RPC 调用，server 执行后返回结果。

**传输方式**（底层 JSON-RPC 2.0）：

- **stdio**：server 是本地子进程，走标准输入输出——适合跑在自己机器上的本地能力；
- **Streamable HTTP**：server 是一个 URL 端点——适合远程服务与官方托管 server，支持 SSE 流式响应。

连接时握手后客户端拉取 `tools/list` 获得能力清单。

**生态**：数千个现成 server（GitHub、Google Workspace、Slack、Postgres、文件系统……），多个注册中心（官方 MCP Registry、Smithery、Glama、PulseMCP）。自己写的 server 可被 Kimi Code、Claude Desktop 等任何 MCP 客户端复用；别家写的 server 自己也能直接用。

**MCP 网关**：2026 年出现的网关品类，把 N 个 MCP server 聚合成一个带鉴权/权限管理的端点（开源代表：**Obot**、**Bifrost**；商业代表：Portkey、IBM MCP Gateway 等）。这就是"动作侧大网关"的现成形态。

**局限**（重要，见 2.4 与第 5 章）：MCP 是"动词协议"（调用能力），请求/响应、客户端发起，**不擅长持续事件流**。入向信息聚合以它为主角属于误用。

### 2.2 A2A（Agent2Agent Protocol）

**是什么**：Google 2025 年 4 月发布的开放协议，2025 年 6 月捐给 Linux Foundation，2026 年 3 月发布 v1.0（生产级稳定规范），150+ 组织支持。回答的问题：不同厂商/框架构建的 AI agent 之间如何互相发现、通信、委派任务。

**核心机制**：

- **Agent Card**（能力声明）：每个 agent 发布一个 JSON 卡片，说明自己是谁、会干什么、怎么连接；
- **Task**（任务委派）：客户端创建任务，服务端 agent 异步执行；
- **Message / Artifact**：任务过程中的消息与产出物；
- 传输：JSON-RPC 2.0 / gRPC over HTTP(S)，SSE 流式更新；
- 支持有状态与无状态交互、长时间运行任务、人机协同（HITL）插点。

**与 MCP 的分工**（本架构的座右铭之一）：

> **MCP 管 agent↔工具，A2A 管 agent↔agent。**
> "调用一个能力"用 MCP；"委派给另一个 agent 干活"用 A2A。

### 2.3 CloudEvents

**是什么**：CNCF 的开放标准，用统一格式描述"事件"。它就是入向信息聚合所需的那个"现成的信息收集网关格式"——不需要自己发明。

核心字段：`id`、`source`、`type`、`time`、`subject`、`datacontenttype`、`data`。

**为什么是入向的主角**：入向需要的是"名词协议"（这条信息是什么：谁、什么、何时、多重要），而不是"动词协议"（怎么调用一个能力）。CloudEvents 描述名词，MCP 描述动词。

### 2.4 三大协议的分工总表

| 方向 | 标准 | 角色 | 类比 |
|---|---|---|---|
| 入向（信息流） | **CloudEvents** | 描述"这条信息是什么" | 名词 |
| 出向（动作调用） | **MCP** | 描述"怎么调用一个能力" | 动词 |
| 出向（任务委派） | **A2A** | agent 与 agent 协作 | 委托书 |

### 2.5 UnifiedPush / ntfy（自建推送）

- **ntfy**：Apache 2.0 / GPLv2 双许可的开源推送服务，一条 `curl -d "msg" https://ntfy.sh/mytopic` 就能推送到手机，有官方 Android/iOS App，自托管无限制。
- **UnifiedPush**：Android 上的去中心化推送标准，定义"App 如何被唤醒接收推送"，ntfy 可作为其分发器。要点：UnifiedPush 替换的是 FCM 的"唤醒机制"，App 被唤醒后自己展示通知。

二者是国内"App 被杀后仍能收消息"三通道方案的两个组成部分（详见第 8 章）。

## 3. 网关选型调研

### 3.1 候选分析与对比

**先排除两类"看起来像"的选项**：

- **APISIX / Kong / Tyk（API 网关）**：是"请求代理"（进来的 HTTP 请求路由到后端），本场景是"事件汇聚"（主动抓、被动收、归一化、推出去）。层级不对。
- **EMQX / NATS（消息代理）**：只是总线（负责传），不负责接。Connector 仍然全要自己写。可作网关的"脊柱"，不能当网关本体。

**真正的候选（flow engine / automation engine 品类）**：

| 标准 | Node-RED | n8n | Home Assistant |
|---|---|---|---|
| 原理优雅 | flow + 统一 message 抽象，一切源头都是 `msg` | workflow 是"任务执行"模型，非消息流 | 世界观是"实体当前状态"，非事件流 |
| 性能/开销 | 单 Node.js 进程，<100MB 内存，树莓派可跑 | 重（建议 Postgres，队列模式加 Redis） | 中等（Python，RPi 可跑） |
| 持续运行 | 400 万+ 装机量，工业界 7×24 跑了十年 | 稳定，企业件取向 | 极强，有跑数年的实例 |
| 兼容性 | 3000+ 社区节点，协议怪咖都有 | 2000+ 官方集成，最省心 | 2000+ 集成 |
| 自配置 | 可视化流编辑器，配置即画图 | 同左，模板市场极大 | UI 配置极佳 |
| 2026 年 AI 对接 | node-red-contrib-mcp：可拉 MCP server，也可把 flow 暴露成 MCP tools | 双向 MCP 一等公民（MCP Client node + MCP Server Trigger），自带 LangChain AI Agent 节点、HITL | 内置 conversation agent + MCP 双向集成 + 本地语音管线（2026.8 起 llama.cpp 集成） |

另：**Huginn**（48k stars，self-hosted IFTTT，Ruby，事件流 agent 图）架构思想值得借鉴，但社区与活跃度弱，未入选。**Novu**（开源通知/Agent 通信基础设施）适合参考其"通知编排"数据模型。

### 3.2 结论：网关本体 = Node-RED

理由：它是候选中唯一"生来就是网关"的东西——设计目标（wiring hardware devices, APIs and online services）与本场景一字不差。message 抽象是所有源头信息的最小公分母（原理优雅）；单进程低开销（性能高、开销低）；十年工业级运行记录（持续运行）；3000+ 节点 + MCP 双向能力（兼容性强）；可视化编辑器（自己配置）。七条标准全中。

**备选与替换条件**：若试用后觉得可视化 flow 写复杂逻辑别扭，同位置可替换为 n8n（更重但 AI 节点豪华）或自研 Go 常驻进程（最轻但 connector 全自己写）。网关对外接口（CloudEvents 事件格式 + MCP）已定，换网关不动上下游——技术选型可晚定。

### 3.3 网关职责边界（最重要的纪律）

**网关要"大"，但必须"笨"。Node-RED 里不出现 LLM 调用。**

- **管**：所有源头接入（轮询 RSS/日历、收 webhook、MCP client 拉取、手机通知上报）；归一化为 CloudEvents；三路分发（推手机、喂核心 Agent、触发确定性动作）。
- **不管**：记忆、重要性判断、汇总表达（核心 Agent）；LLM 决策的复杂动作（Agent 调 MCP/A2A 执行）；长期存储（数据库）。

flow 全是确定性的接入/转换/路由逻辑——这条纪律保证网关低开销、可长期运行、行为可预测。

## 4. 总体架构

### 4.1 四层架构

```
[接入层]            [传输层]           [核心层]          [动作层]
各种源头 ──→  网关(Node-RED)  ──→  核心 Agent  ──→  MCP tools / Worker agents / 规则flow
          归一化 CloudEvents      记忆+判断+路由        (确定性)    (开放式)   (固定模式)
                ↓ 推送通道                          ↑ 动作结果/任务回报作为事件回流
              手机(App) ◀──── 语音/TTS 播报 ────────┘
```

- **接入层**：Node-RED + 四种接入手段（见第 5 章）；
- **传输层**：三通道保活（见第 8 章）；
- **核心层**：唯一的核心 Agent（见第 6 章）；
- **动作层**：MCP tool / Worker agent / Node-RED 规则 flow 三条腿（见第 7 章）。

### 4.2 星型拓扑

```
                    ┌────────────────────────────────────────┐
                    │              VPS 服务器（常驻核心）       │
                    │                                         │
                    │  Node-RED 网关 ──(MCP client)──┐        │
                    │     ↓ CloudEvents               ↓ 拉取   │
                    │  核心 Agent(Host, 内嵌 MCP clients)     │
                    │     ↓ 调 tools                          │
                    │  MCP servers 群（动作侧）:                │
                    │   · IM bot MCP · 数据库/记忆 MCP          │
                    │   · 繁琐定制程序 MCP                     │
                    └──────▲──────────────────▲───────────────┘
                           │ HTTP/本地         │ A2A 任务委派
              ┌────────────┴───────┐  ┌───────┴──────────┐
              │      你的电脑        │  │  第三方官方托管    │
              │  本地 MCP servers:  │  │ (谷歌日历等远程    │
              │   · 文件系统/本地程序 │  │  MCP server,     │
              │   · Kimi Code       │  │  零部署)          │
              │     headless(A2A)   │  └──────────────────┘
              └─────────────────────┘

   手机: 瘦客户端 + 可选的"手机能力 server"
     上行: 通知监听 → webhook → 网关
     下行: ntfy 推送 ← 网关(包装成 agent 的 notify_user tool)
```

**关键工程细节：所有外围机器（家里电脑、办公室电脑、树莓派）只做出站连接**（MQTT/WebSocket/A2A）到 VPS。NAT/防火墙后面的设备无需公网 IP、无需内网穿透；VPS 是唯一暴露的端点。

### 4.3 全链路事件流（一次完整的"听到→处理→回报"）

以"你戴着耳机说：把我电脑上那个报告整理一下，发给我摘要"为例：

1. 耳机麦克风 → 手机 App（本地 ASR 或云端）→ 文本经长连接/推送上行 → VPS 网关；
2. 网关归一化为 CloudEvents（type: `user.command.spoken`）→ 核心 Agent；
3. 核心 Agent 理解意图，识别"目标机器 = 家里的电脑"，查记忆确认"那个报告"指什么；
4. 通过 A2A 向 PC worker agent 委派任务单（含目标、约束、workspace 路径、回调地址）；
5. PC worker 异步执行（10 分钟~2 小时），核心 Agent 不阻塞；
6. worker 完成 → 回报事件（PC worker → 网关 webhook → CloudEvents: `agent.task.completed`）→ 核心 Agent；
   **注意：这条回报通道就是需求清单里的"某个电脑的 agent 任务完成"——派出与收回是同一个环，不是两套系统；**
7. 核心 Agent 判断"值不值得现在打扰用户"，生成摘要；
8. `notify_user(text, priority)` → ntfy/推送 → 手机 TTS → 耳机："报告整理完了，要点是……"

## 5. 入向设计：信息聚合

### 5.1 统一事件格式：CloudEvents

所有源头，无论经哪种手段接入，出网关时必须是 CloudEvents（完整字段定义见附录 B）。核心设计：**`actions_available` 字段**——每条入向事件自带"这个源允许哪些动作"。

这使得"看到什么"与"能做什么"在核心 Agent 的认知里统一：入向事件携带能力声明，出向动作调用 MCP tools，两者对 Agent 是同构的——**系统最优雅的一个闭环**。

### 5.2 四种接入手段

| 手段 | 适用源 | 实现 | 与 MCP 关系 |
|---|---|---|---|
| ① Webhook | GitHub、电脑 agent 回报、手机通知上报、自建系统回调 | Node-RED `http in` 节点直接收 | 无关（入向大头） |
| ② 轮询 | RSS、定时 API（天气等） | `inject` 定时 + HTTP 请求节点，或社区节点 | 无关 |
| ③ 协议长连接 | 邮件 IMAP、Telegram Bot long polling、MQTT 设备 | 对应原生节点 | 无关 |
| ④ MCP 拉取 | 有现成优质官方/社区 MCP server 的源（日历、Gmail） | node-red-contrib-mcp | **MCP 在此只是一种 connector 语法，不是骨架** |

第 ④ 类的价值是复用现成 server 与统一鉴权；不追求"万物皆 MCP"。

### 5.3 各源头的具体接入方案

| 源头 | 方案 | 说明 |
|---|---|---|
| 封闭 IM（微信等，产品不接入） | **不做任何集成**；消息由通知监听在系统层只读捕获 | 零封号/零政策风险；双向动作仅面向开放协议 IM（Telegram Bot、Matrix、Slack webhook 等） |
| 一切手机 App 通知（课程 App、短信、无 API 的 App） | 手机 App 用 **NotificationListenerService** 监听 → HTTP 上报网关 | 系统级兜底，能读不能回；双向交互靠官方 bot 接口 |
| 日历（谷歌/CalDAV） | 官方托管 MCP server 或 HA 集成 | 零部署或近零部署 |
| 天气/新闻 | 轮询类：定时 inject + HTTP；RSS 用社区 feed 节点 | 模板化 |
| 工作待办 | 视系统：有 MCP 用 MCP，有 webhook 用 webhook | — |
| 电脑 agent 任务完成 | worker 出站上报 webhook / MQTT | 零难度 |
| 电话/短信状态 | 手机 NotificationListenerService 已覆盖短信通知；发送类动作留给"手机能力 server"（见 8.3，一期不做） | — |

### 5.4 过滤与分级（事件到达 Agent 之前）

- **网关规则层先做掉大部分**：静音时段降级、关键词过滤、同源合并（群聊连发合并为一条）、低频源聚合摘要；
- 剩下的事件按 `priority_hint` 分级进入 Agent；
- Agent 只做"这批剩下的值不值得说、怎么说"。

健康的流量分布：**大部分事件死在过滤器，大部分动作停在 tool 层，只有个位数百分比抵达 worker agent。** 若每日 agent 任务超过十几个，说明该把高频模式沉淀成固定 flow——系统随使用"变聪明"（常用路径固化成规则）而不是"变贵"。

### 5.5 推送与检阅分离：收件箱模型

**原则：push 只负责"告诉你有新事"，检阅靠按需同步**（邮差敲门 ≠ 信箱取信，电子邮件模型）。

- **全量持久化（一期必需，非后加）**：所有事件存入服务器"收件箱"（数据库，按源分文件夹）。它是 push/sync 分离的前提，也是换机不丢历史、多设备同时检阅的基础；
- **实时**：推送敲门——"课程群 有 3 条新消息（经通知监听）"，不含全文；
- **检阅**：App 打开时增量同步——`GET /inbox?since=<上次同步 token>` 返回增量事件 + 新 token；断点续传、离线缓存天然成立。参考 Matrix `/sync` API 的设计（可借鉴；一期自实现分页 API，不上 Matrix）；
- **回复**：检阅时每条消息带 `actions_available`，点"回复"即上行动作请求，走 MCP/A2A 执行——检阅与动作在同一界面闭环；
- **杀后台零丢消息**：推送唤醒 → 重连 → 用 `since` token 补齐断线期间增量。

## 6. 核心 Agent 设计

### 6.1 位置与唯一性

**核心 Agent 只有一个，住在 VPS。** 不在开发机（合盖即死），不分散到源头（汇总需要全局视野；记忆需要单一权威副本；成本只需一份）。

三个层级别混淆：

| 层级 | 是什么 | 住哪 | 智能量 |
|---|---|---|---|
| 核心 Agent | 唯一的大脑：判断重要性、汇总、记忆、决策动作 | **VPS** | 全量 LLM |
| 源头 connector | Node-RED flow / MCP server，只做"抓→转→发" | 跟源头或 VPS | **零（故意的）** |
| Worker agent | 被委派干活的执行者 | 资源所在机器 | 任务内执行智能，不管"用户该知道什么" |

口诀：**智能集中（一个大脑）、执行分散（worker 住资源旁）、连接无智（connector 只是管子）。**

### 6.2 记忆

- 选型：**Letta**（原 MemGPT，Apache 2.0）：为"长期运行 + 记忆"而生的 agent 运行时，核心记忆 + 递归记忆架构正合"不断接收、汇总、反馈"场景；
- 备选：LangGraph（自编排）+ Mem0（纯记忆层）；
- 分工：用户画像、"什么重要"归核心 Agent；worker 可有任务级本地记忆。

**2026-09 重要修订：核心 Agent 运行时优先评估 OpenClaw / Hermes，自研/Letta 降为备选。** 社区已出现两大成熟的自托管个人 agent 运行时，与本设计收敛于同一架构（常驻 agent + 消息网关 + MCP + 技能/记忆体系）：

- **[OpenClaw](https://openclaw.ai/)**（380k+ stars，MIT，OpenClaw Foundation）：本地优先个人 AI 助手，一个 Gateway 进程连接 24 个聊天平台，用户直接在已有聊天 App 里使用；配对模型、Dashboard、沙箱、ClawHub 技能市场；"不装新 App，用已有聊天 App 当客户端"是其病毒式传播的关键；
- **[Hermes Agent](https://blakecrosley.com/guides/hermes)**（191k+ stars，Nous Research）：自我改进 agent——任务后自动沉淀 Skill、失败自动学习；CLI + 15+ 消息平台网关，**原生内置微信 iLink Bot 官方协议**；MCP 原生，可兼作 MCP server。

**策略转变**："agent + 网关 + MCP" 层已被商品化，不应重造。本项目重新定位为**上述生态之上的差异化层**：可穿戴音频输出（TTS 播报 / 预渲染音频 / 耳机优先）、通知监听全捕获、CloudEvents 事件收件箱（push+sync）、多机 worker 联邦（A2A）、国内落地（三通道保活）。

### 6.3 任务路由：一个意图的五个归宿

核心 Agent 收到意图后（语音指令或事件触发）按序判断：

```
意图进来
  ├─ ① 纯对话/咨询？"今天我还有什么事？"
  │     → Agent 自答（查记忆 + data 型 MCP 资源，不调动作）
  ├─ ② 确定性动作？输入明确、步骤固定、结果可预期
  │     （"会议改到 10 点""记到待办"）
  │     → 直接调 MCP tool，秒级返回
  ├─ ③ 固定模式任务？"每晚 10 点推明日日程"
  │     → Node-RED 定时 flow，零 LLM，永不过 agent
  ├─ ④ 开放式任务？"整理电脑上那个报告"
  │     → 派 worker agent（A2A）
  └─ ⑤ 混合型？→ 拆解：确定性部分→②，开放部分→④，
        通知→notify tool，记账→①
```

路由依据三问：**步骤固定吗？输入明确吗？结果可验证吗？** 全是"是"就往低走，任一"否"就往高走。

### 6.4 成本金字塔

```
        ┌──────────────┐
        │ worker agent   │ 最贵：LLM 全程驱动，分钟~小时级
      ┌─┴──────────────┴─┐
      │ Agent 自答/调 tool │ 中：一次或数次 LLM 调用
    ┌─┴──────────────────┴─┐
    │   Node-RED 规则 flow   │ 近零成本：纯确定性
    └──────────────────────┘
    过滤器：事件在此被丢弃/降级，不上报
```

设计通则：**每个任务都路由到"能完成它的最便宜的层"——规则能做的事不麻烦 tool，tool 能做的事不麻烦 agent。**

## 7. 出向设计：动作分发

### 7.1 总原则

核心 Agent 自己永远不"干活"，只做调度——**决定什么事、派给谁、结果怎么告诉用户**。真正在其他机器上做事的是下面三条腿。

### 7.2 决策规则：能用 tool 就不用 agent

用户提出的三个动作例子，只有第一个需要 worker agent：

| 目标 | 形态 | 理由 |
|---|---|---|
| 在电脑上做**开放式**任务（整理报告、跑代码） | **Worker Agent**（A2A） | 需现场推理、多步操作、处理意外 |
| 那个繁琐庞大的**定制程序** | **直接包成 MCP server**，不套 agent | 程序是确定性的，套 agent 纯属多一层开销与不确定性 |
| 谷歌日历等第三方 | **MCP server**（官方托管或自架） | 同上 |

每多一个 agent，多一份 token 开销与行为不确定性。**Agent 层只出现在"那台机器上确实需要开放式智能"的地方。**

### 7.3 MCP 动作层

- 所有确定性能力（含第三方）统一封装为 MCP server，对核心 Agent 暴露为整齐的 tools；
- 2026 年可选开源 MCP 网关（Obot / Bifrost）把几十个 server 聚合成一个带权限管理的端点——即"动作侧大网关"的现成形态，可后期引入；
- 每个走 HTTP 的 server 必须加鉴权（token 或 OAuth），否则能力裸奔在公网。

### 7.4 Worker Agent 层（A2A 委派）

**生命周期**：

```
queued → assigned → running → done / failed / awaiting_input
```

- **任务单**：`{id, target_agent, goal, context, constraints, workspace, callback}`；
- **异步**：任务可能 10 分钟~2 小时，核心 Agent 委派后不阻塞，事件驱动；
- **awaiting_input（反问链）**：worker 干到一半发现歧义，沿原路反问：worker → 核心 Agent → 耳机问用户 → 回答原路流回。全链路无同步等待；
- **离线**：任务在网关排队（MQTT 离线消息队列天然支持），worker 上线拉取；
- **失败**：worker 上报原因 → 核心 Agent 决定重试 / 换机 / 升级询问用户，而不是直接弹一堆报错；
- **重启恢复**：每台 worker 机器跑守护进程，开机自启、自动重连注册。

**权限分级**（对应用户提出的多种 worker 形态）：

| 级别 | 权限 | 用途 |
|---|---|---|
| workspace 限定型 | 只读写固定文件夹 | 默认形态，大多数任务 |
| 全机型 | 整台电脑 | 需按任务类型显式授权 |
| 有记忆型 | 跨任务记忆住本地 | "用户画像/什么重要"仍归核心 Agent |

每个 worker 独立身份与凭证，核心 Agent 按任务类型路由到对应权限的 worker。

**worker 注册表**：每台机器一个小 daemon，启动时向 VPS 注册自己的 Agent Card（能力、权限级别、在线状态）。

### 7.5 输出闭环：notify_user 也是 tool

"播报给用户"封装为一个 MCP tool：`notify_user(text, priority)`——VPS 上一个薄 MCP server，内部调 ntfy/推送通道。

**输出通道与输入源用同一种协议统一**，这是 MCP 世界观里最优雅的部分：Agent 眼里，"感知世界"和"作用于世界"是同构的 tools 调用。

## 8. 传输层与手机端

### 8.1 三通道保活（国内 Android 的硬问题，无魔法，业界成熟组合）

1. **厂商推送通道**（MiPush / HMS / OPPO / vivo / FCM 海外）：App 被杀后唯一能唤醒它的东西，国内必须接；
2. **自托管 ntfy**（UnifiedPush 标准分发器）：服务器 → 手机的独立通道，HTTP PUT 即发，不依赖任何第三方云；
3. **前台服务 + 电池优化白名单**：保活期间跑 WebSocket/MQTT 长连接收实时事件（包括语音指令上行）。

分工：被杀时靠 ①② 唤醒（高延迟容忍的通知）；存活时靠 ③（实时双向语音/事件）。

### 8.2 播报三层保障（App 被杀仍可"听到"）

| 层 | 触发条件 | 机制 |
|---|---|---|
| L1 实时播报 | App 存活（常态） | 前台服务长连接收事件 → TTS → 蓝牙媒体通道 → 耳机 |
| L2 推送唤醒 | App 被杀 | 高优先级厂商推送唤醒 App → Android 给予约 20 秒后台执行窗口 → 跑 TTS 到耳机 |
| L3 音频兜底 | App 被杀/冻结只剩通知能力 | Agent 播报文本由 VPS 预渲染为数十 KB 音频文件，推送带 URL；App 唤醒后下载并**设为通知音播放**——冻结状态也能响 |

- L3 代价是服务器要跑 TTS：仅对需播报事件渲染，静默事件不渲染，控制成本；
- iOS 对通知自定义音频限制严格（长语音需专门 entitlement），**产品形态 Android 优先**。

### 8.3 手机 App 定位

**瘦客户端**，四件事：

1. **上行采集**：NotificationListenerService 监听全部通知 → 过滤（去敏感）→ HTTP 上报网关（覆盖一切无 API 的 App）；
2. **下行呈现**：收推送，TTS 播报（可接耳机/眼镜）；
3. **语音交互**：唤醒词（本地 sherpa-onnx，离线、中文好）+ ASR + 上行；
4. **可选——"手机能力 server"**：把发短信、通讯录、定位、TTS 暴露为 MCP server 供 Agent 调用。**一期不做**（server 要常驻，与杀后台冲突）；需要"从本机号码发短信"等能力时再做，或改用云端短信 API 绕过。

**手机不做的事**：不嵌核心 Agent，不做 MCP client（只对网关说话），不做轮询。

### 8.4 连接模型：端点（Endpoint）× 宿主（Host）× 适配器（Adapter）

**纠错（2026-09-15）**：连接的基本单元不是"设备/机器"，而是**端点**——VPS 要连的东西各式各样：一个文件夹、一台机器、一个监听端口、一个程序、一个云账号。机器只是某些端点的宿主。

统一抽象：

```
端点 Endpoint = 用户配置和认知的逻辑单元
  · kind        适配器类型（folder-watch / port-listen / http-poll / webhook-in /
                im-bot / cloud-api / mcp-server / a2a-agent / process / db / serial ...）
  · direction   source（采集）/ sink（动作）/ both
  · locator     位置描述（路径、host:port、URL、账号、串口名）
  · credentials 独立凭证
  · schema      产出事件类型 / 接受的动作清单

宿主 Host = 端点的实际执行位置，只有三种：
  ① VPS 内置宿主：connector engine 直接托管"VPS 可达"的端点
    （RSS/http-poll、webhook 入口、cloud API/OAuth、IMAP、远程 MCP server）
  ② 现场 daemon：跑在 NAT 后机器上的常驻进程，托管"VPS 够不着"的端点
    （folder-watch、本机端口、串口/USB、本地文件、本地程序、worker agent）
  ③ 第三方托管：官方云服务

适配器 Adapter = kind 的实现；daemon 入职时注册的不是"一台设备"，
                 而是适配器能力清单（"我能跑 folder-watch / port-listen / a2a-agent"）
```

连接机制只有两种，殊途同归汇入 CloudEvents/MCP 总线：

- **VPS 直连**（宿主①）：VPS 对端点直接发起（轮询/连接/Webhook 接收）；
- **daemon 代管**（宿主②）：daemon 入职一次（引导方式见下），VPS 把端点配置下发给声明了对应能力的 daemon 执行；事件经其出站长连接上行（`seq` 去重、`since` 游标补拉）。

各类端点落位示例：

| 用户要连的"东西" | 端点 kind | 宿主 | 适配器行为 |
|---|---|---|---|
| 一个文件夹 | `folder-watch` | ② | 监听目录变更 → 事件上行 |
| 一台设备（摄像头/树莓派） | `mqtt-device` / `port-listen` | ② 或 ① | 采集状态/传感数据 |
| 一个监听口（本机 :8080） | `http-poll` / `tcp-probe` | ② | daemon 代为轮询/探活 |
| 一个繁琐定制程序 | `process` / `mcp-server` | ② 或 ① | 包装成 MCP tools 暴露 |
| 一个云账号（Gmail/日历） | `cloud-api`（OAuth） | ① | VPS 直接拉取/执行动作 |
| 一个 IM 群（Telegram） | `im-bot` | ① | 双向消息收发 |
| 一台电脑当工人 | `a2a-agent` | ② | 接任务单、干活、回报 |
| 一个串口/USB 设备 | `serial` | ② | daemon 本地读写 |

**关键：文件夹/端口无需各自入职**——它们生活在 daemon 的信任域内；daemon 入职一次，VPS 即可向其下发出任意多个端点配置。注册粒度 = 宿主；配置粒度 = 端点。

**daemon 入职流程**（两种引导，默认配对码）：

1. **配对码**（零复制粘贴，如手机-only 用户给电脑装机）：目标设备运行公开安装命令 → 终端打印 6 位配对码 → 用户在 App"添加设备"手输 → VPS 绑定；
2. **令牌注入**：App"添加设备"→ VPS 发一次性注册令牌（10 分钟有效）→ 显示为安装命令 → 设备运行后令牌换长期凭证；
3. 入职即注册：daemon 提交公钥 + 适配器能力清单 → 领取 `{daemon_id, 长期凭证}` → 建立出站 MQTTS/WSS 长连接（443，心跳 30~60s，断线指数退避重连）；
4. 注册表：`hosts` 表（id、名称、适配器能力、公钥、权限范围、last_seen），App 设备页实时可见；手机 App 登录账号即其宿主身份，非特殊通道。

安全：凭证按最小权限签发（上报型宿主拿不到动作权限）；daemon 只能收到其**已声明并被授予**的适配器类型的端点配置；`port-listen`、`process` 等敏感适配器默认关闭、显式授权；高敏场景上双向 TLS。

### 8.5 下行管道与回执（手机如何收到 Agent 的回复）

Agent 决定通知 → `notify_user` tool → VPS 通知服务 → 按优先级三路下行：

| 优先级 | 条件 | 机制 |
|---|---|---|
| ① 实时 | App 存活（前台服务长连接） | WSS 直达 → TTS → 蓝牙媒体通道 → 耳机，亚秒级 |
| ② 唤醒 | App 被杀 | 高优先级厂商推送（MiPush/HMS/OPPO/vivo/FCM）→ 20 秒后台窗口 → 下载预渲染音频 → 创建临时通知 channel（自定义铃声）→ 响铃播报 |
| ③ 兜底 | 厂商通道也失败 | ntfy 通道纯文本通知 + 收件箱未读红点（用户打开 App 补听） |

**回执链**：手机收到/播报/已读都会经可用通道回传 `ack {notification_id, state}`；未确认按策略升级（silent → sound → 全屏提醒）。

**诚实边界**：被杀状态下"收听播报 + 看通知"成立，语音对话不成立（需要麦克风）；交互前必须先打开 App（或依赖存活期的唤醒词）。

### 8.6 格式的归一化：负载原型、映射 DSL 与样本驱动配置

**问题**：每个端点的进出数据格式截然不同（JSON API、原始文本、二进制帧、邮件 RFC822……）。

**总原则：不统一世界的格式，只统一系统的边界。** 系统内部只有两种格式，格式差异被吸附在适配器的三档归宿里：

| 档 | 适配器 | 格式差异归谁 | 用户配置量 |
|---|---|---|---|
| T1 | 固定适配器（Gmail/Telegram/日历/标准 MQTT……） | 映射写死在代码 | 零 |
| T2 | 通用适配器（webhook-in/http-poll/serial/file-watch/tcp） | 映射 DSL，用户标注语义 | 一次/端点，样本驱动 |
| T3 | 自带适配器（按开放契约自写，填 URL 接入） | 用户自己的代码 | 零 UI 工作 |

**系统内部的两种格式**：

- 入向：CloudEvents 信封（固定）+ `data` 负载，负载按**少量负载原型**（archetype）组织：

| 原型 | 字段骨架 | 适用 |
|---|---|---|
| `message` | actor/title/body/thread | IM、邮件、通知 |
| `metric` | name/value/unit/tags | 传感器、探针 |
| `file` | path/op/size | 目录监听 |
| `task` | state/summary/progress | worker 回报 |
| `calendar` | title/start/end/location | 日程 |
| `alert` | severity/source/description | 告警 |
| `result` | ok/error/detail | 命令/查询结果 |

适配器声明其产出原型；Agent 的摘要与播报策略按原型区分。出向：动作以 MCP tool schema 声明，表单由 schema 自动生成。

**T2 的样本驱动配置（用户从不写转换逻辑，只标注语义）**：

1. 添加端点，选适配器，填连接参数（串口/URL/路径）；
2. 系统提示"粘贴一条收到的原始数据样本"；
3. 系统自动推断映射（JSON：按类型与字段名建议 JSONPath；文本：建议正则；可选 LLM 辅助猜，本地规则推断保底）；
4. 用户在字段对应表上确认/微调（左列原型字段，右列提取表达式）；

```yaml
adapter: serial
archetype: metric
decode: { content-type: text, pattern: "HUM:([\d.]+);TMP:([\d.]+)" }
fields:
  value:  { capture: 1 }             # 系统建议
  name:   { const: "soil-humidity" }  # 用户补语义
  unit:   { const: "%" }
  time:   { now: true }
```

5. **实时预览**生成的 CloudEvents（所见即所得）；
6. **发送测试事件**：走完整管道到收件箱/耳机——配置即验收。

出向（通用动作适配器）配**请求模板**：`POST http://{{device.host}}/ctrl`，body `{"op":"dim","level":"{{args.level}}"`。

**设计成立的理由**：T1 吃掉大多数源；T2 的 DSL 有界（只做"原始→原型"标注，不图灵完备）所以能推断、能预览、能测试；T3 吃掉长尾且不算私货。映射存于端点 config，随备份导出、随模板市场分享。

## 9. 部署方案

### 9.1 部署地图（MCP server/client 放哪）

判断标准：**谁要调能力，谁的肚子里嵌着 client（跟着宿主走）；谁提供能力，谁就是 server——server 按"能力所涉资源在哪"来部署。**

| server 类型 | 住哪 | 传输 | 例子 |
|---|---|---|---|
| 纯 API 型、无状态 | **VPS** | Streamable HTTP | 日历、天气、IM bot、定制程序封装、记忆数据库 |
| 要碰本地资源 | **资源所在的机器** | stdio 或本地 HTTP | 文件系统、本地程序、Kimi Code headless |
| 第三方官方提供 | 不用部署 | 远程 HTTPS + OAuth | 谷歌等官方托管 MCP server |

各处的 client 嵌在谁身上：

- **VPS**：Node-RED（信息侧 client，拉 data 型 server）+ 核心 Agent（动作侧 client，调 action 型 server）。同一个日历 server 可两边都连（网关读事件，Agent 建日程）；
- **你的电脑**：Kimi Code 自己就是宿主（自带 client 用本地 server）；对核心 Agent 而言它又是一个 A2A worker；
- **手机**：不嵌 client。

### 9.2 服务器 Compose 栈（一台 VPS，六个服务）

```yaml
services:
  node-red:        # 网关本体：接所有源、归一化 CloudEvents、分流
    image: nodered/node-red
    volumes: [./node-red-data:/data]
  ntfy:            # 自建推送通道（App 被杀后的兜底）
    image: binwiederhier/ntfy
    command: serve
    volumes: [./ntfy-data:/var/cache/ntfy]
  emqx:            # 内部总线：worker/设备出站接入、离线队列
    image: emqx/emqx
  agent:           # 核心 Agent（Letta 或自研，订阅网关事件流）
    build: ./agent
  mcp-servers:     # 动作侧 server 群（日历、定制程序封装、notify_user……）
    build: ./mcp-servers
  caddy:           # 反向代理 + 自动 HTTPS，对外唯一暴露口
    image: caddy
```

数据存储：Node-RED 内置 SQLite 起步；Agent 记忆随运行时（Letta 或 OpenClaw/Hermes 自带）；事件收件箱入库为一期必需（见 §5.5）。

### 9.3 开发机与部署的分工

- **开发机** = 写 flow、改 Agent 代码、本地 `docker compose up` 调试；
- **VPS** = 同一份 compose 常驻运行；
- 开发机同时是 **worker 宿主**（Kimi Code headless 住这，A2A 接任务）。

### 9.4 安全清单

- 所有走 HTTP 的 MCP server 必须鉴权（token/OAuth）；
- Caddy 是对外唯一端口；Node-RED 编辑器必须开认证且不进公网（SSH 隧道管理）；
- webhook 端点带随机路径 + 签名验证；
- 手机上报通道 TLS + 设备 token；
- ntfy topic 名用高熵随机串；
- worker 凭证按权限分级发放，最小权限；
- 敏感源（IM 内容等）考虑端到端加密存储。

### 9.5 产品化与多租户部署形态

三种部署形态（宣传时主推第一种；自助配置流程详见后续讨论定稿后增补）：

| 形态 | 用户体验 | 成本 | 适合 |
|---|---|---|---|
| **官方托管**（运营方运维的公共网关） | 注册即用 | 运营方承担 | 宣传、拉新、普通用户 |
| **一键脚本**（用户自带 VPS） | `curl \| bash` 或云厂商自定义数据粘贴，QR/令牌配对 | 用户自担 VPS | 进阶用户（**本阶段设计重点**） |
| **compose 自架** | Docker 手动起 | 零 | 极客 |

多租户隔离：按账号分命名空间（独立 topic 前缀 / 事件流 / 收件箱视图），EMQX ACL + ntfy access token 实现。

### 9.6 星型连接的规模化

- 单台 VPS 支撑数千~数万并发 TLS 长连接（每条空闲连接数十 KB 内存）；EMQX 水平为百万级；
- 端口用 443/8883，穿透力最强；心跳 30~60s 维持 NAT 映射；断线指数退避重连，重连后以 `since` token 补拉增量（配合 §5.5）；
- 唯一代价是服务器带宽成为设备间流量瓶颈：个人文字/语音事件无感；若出现大文件直连需求，升级为"服务器做信令、设备 NAT 打洞直连（WebRTC/Tailscale 模式）、失败回落中继"——优化而非替代。

## 12. 落地路线图

**Phase 0 — 最小闭环（1~2 天）**
1. VPS 起 compose：Node-RED + ntfy + Caddy；
2. 一个测试源（curl webhook 或一个 RSS）→ Node-RED 归一化 → ntfy 推到手机；
3. 验证"服务器 → 被杀的 App → 屏幕亮起"链路。

**Phase 1 — 真源接入（1~2 周）**
4. 接通知监听上报 + 一个开放协议 IM（Telegram Bot）+ 一个日历 MCP server；
5. 写 3~5 条过滤/合并规则 flow；
6. 手机 App（或先用现成工具原型）：NotificationListenerService 上报 + 收推送播报。

**Phase 2 — 核心 Agent（2~4 周）**
7. 起 Letta Agent，订阅 CloudEvents 流；
8. 分级流水线：规则过滤 → 小模型摘要 → 大模型只处理重要事件；
9. notify_user tool 打通；语音指令上行打通。

**Phase 3 — 动作层（持续）**
10. 第一个确定性 MCP tool（日历建事件）；
11. PC worker daemon + A2A 委派 + 任务回报回流；
12. 把高频任务模式沉淀为规则 flow（系统开始"变聪明"）。

**Phase 4 — 硬件与打磨**
13. 本地唤醒词/ASR（sherpa-onnx）降低云端依赖；
14. 评估 Omi / 眼镜路线；
15. 引入 MCP 网关（Obot/Bifrost）统一权限。

## 13. 风险与坑

| 风险 | 等级 | 应对 |
|---|---|---|
| 通知监听能读不能回 | 中 | 封闭 IM（微信）不提供回复动作；开放协议 IM（Telegram/Matrix）有官方 bot API 可双向 |
| 国内 Android 杀后台无银弹 | 高 | 厂商推送 + ntfy + 前台服务三通道，缺一不可 |
| 全事件进 LLM 的成本爆炸 | 高 | 分级流水线 + 路由最便宜层原则 + 模式固化成 flow |
| Agent 行为不确定性破坏"每天可靠运行" | 中 | 95% 确定性工作由规则/tool 承担；Agent 只碰 5% |
| HTTP 暴露 MCP server 的安全面 | 中 | 全量鉴权 + Caddy 单口暴露 + 签名 webhook |
| 链路累积延迟（ASR→Agent→TTS） | 低 | 全异步事件流；播报允许秒级延迟；语音指令链路单独优化 |
| 封闭平台政策漂移 | 低 | 已规避——产品对微信零集成，不受其政策影响 |
| 自研 agent 层与成熟开源项目重复造轮子 | 中 | 核心 Agent 基于 OpenClaw/Hermes 生态构建，自研仅限差异化层（音频/收件箱/联邦/国内落地） |

## 14. 设计原则总结

1. **网关要"大"但必须"笨"**：Node-RED 无 LLM，只做接入/归一化/分发；
2. **出向统一靠 MCP（动词），入向统一靠 CloudEvents（名词），委派统一靠 A2A（委托书）**；
3. **一个大脑（VPS 唯一）+ N 双手（worker 住资源旁）+ 一批无生命的工具（MCP server）**；
4. **路由到最便宜的层**：规则 > tool > agent；
5. **智能集中、执行分散、连接无智**；
6. **star 拓扑，全部外围机器出站连 VPS**，NAT 后无忧；
7. **输出通道也是 tool**（notify_user），感知与作用对 Agent 同构；
8. **星型中央是枢纽不是终点**：Node-RED 可替换（n8n/自研），接口（CloudEvents+MCP）已定，换件不动全身；
9. **复用生态，不重造商品化的层**：agent 运行时/消息渠道/技能市场用 OpenClaw/Hermes 生态；自研精力只投在无人做的差异化层（可穿戴音频、通知全捕获、事件收件箱、多机联邦）。

## 15. 可行性评估

**总结论：能实现，值得做。** 系统约 80% 是装配已被大规模验证的成熟件，无技术悬崖；难度集中在工程打磨与两个外部依赖。

### 15.1 组件风险体检（摘要）

- **零风险**：连接器引擎/Node-RED、CloudEvents 归一化、EMQX 星型出站长连接、ntfy、收件箱增量同步（Matrix /sync 先例）、OpenClaw/Hermes 运行时、MCP 动作层、A2A 委派、通知监听、TTS/唤醒词、反向配对脚本、证书固定；
- **中风险**：保活三通道与 L2/L3 音频兜底（各家 ROM 边角 case 需逐个磨）；
- **中高风险**：无遗留——原最大外部依赖（微信官方协议）已随"零微信集成"立场（见 §1.2）从系统中消除；现存外部依赖（厂商推送通道、LLM 供应商）均有成熟多选备胎。

### 15.2 四个真正的项目杀手（都不是技术）

1. **范围蔓延**——同时做硬件/iOS/托管版/模板市场必拖垮单人项目；解药 = 路线图纪律，每个 Phase 有可独立使用的产物；
2. **ROM 适配打磨**——保活三通道在各品牌系统上的边角行为需逐个实测，琐碎但不可省；
3. **单人带宽**——首条播报 2~4 周（兼职）；完整自用闭环 2~3 个月；可宣传产品再加 3~6 个月；
4. **过早产品 polish**——Phase 0/1 一律用简陋手段（curl/命令行/现成 App）验证闭环后再投 UI。

### 15.3 两个边界

- **"自己用"与"产品化"是两个可行性等级**：后者技术成立但重心转为运营（托管成本、商店审核、用户支持）——故自助 VPS 脚本优先，托管版押后；
- **"零私有协议"信条降低风险**：每个组件都有备胎（EMQX↔NATS、ntfy↔Gotify、OpenClaw↔Hermes、引擎↔Node-RED），换件不动全身。先例：Home Assistant（零发明、纯装配起家）。

## 16. 完整用户旅程

主线场景：**用户已有一台 VPS（或按向导现买），全程只用手机完成配置**。

### 16.1 拿到软件：第 0 天，约 10 分钟

1. 应用商店安装 App，打开；欢迎页三选一：**官方托管**（注册即用）/ **连接我的 VPS**（本主线）/ 高级自架（compose）；
2. 选"连接我的 VPS" → 选云厂商（阿里云/腾讯云/Hetzner/其他）→ App 生成安装脚本（secrets 已全部内嵌）并给出图文指引；
3. 用户按指引在控制台创建实例，把脚本整段粘进"自定义数据"框，点创建（已有 VPS 的用户走网页终端粘贴版）；
4. 回到 App："正在等待你的服务器上线……"（App 用本地预存令牌轮询 health）；
5. 约 3 分钟后：**✅ 服务器已连接**——配对全程自动，用户没有抄写过任何令牌。

### 16.2 首配清单：第 0 天晚，约 30 分钟，全程手机

App 呈现六步清单，每步 5 分钟内：

1. **通知权限 + 电池白名单**：App 识别机型（如小米 15），给逐步图文指引；完成点"已设置"；
2. **第一个信息源**：推荐列表点"RSS 订阅"，粘贴链接保存；
3. **播报测试**：一键发出测试事件 → 耳机响起"测试播报：你的系统已就绪"——用户第一次"听到"系统；
4. **接入一个开放协议 IM**：选 Telegram → 跳转授权 → 显示"Telegram 已连接"；
5. **添加电脑 worker**：电脑浏览器打开官网一行安装地址 → 终端显示 6 位配对码 → 在 App 输入 → 设备列表出现"家里的电脑 · 在线"（全程零复制粘贴）；
6. 全部打勾 → "你的个人 agent 已上线"。

### 16.3 日常使用

**被动收听（主形态）**，事件按重要性分级播报：

- 单条重要（Telegram）："项目组有新消息：明天例会改为线上。需要回复吗？"——用户随口"回复好的" → 数秒后"已回复"；
- 合并播报："通知栏新增 5 条消息（含微信 2 条，只读），其中 1 条需要你处理"；
- 静音时段不打扰；天气突变、会议 15 分钟前、快递到达等按用户画像排序插播；
- worker 任务回报："报告已整理完。摘要：……文件在桌面/报告。要读全文吗？"

**主动交互**：唤醒词 → 语音：

- "今天我还有什么事？"（查记忆 + 日历 + 待办）
- "把这条记到待办""提醒我 6 点买牛奶"
- "帮我把电脑上那个 PDF 合并一下" → "已派给家里的电脑，完成后告诉你"

**检阅（想看时）**：打开 App 收件箱——

- 按源分组的历史列表，下拉触发增量同步（断点续传、离线可看）；
- 每条消息下方动作按钮（回复/稍后/完成/加入日历），回复打字或语音，经官方协议发出；
- 搜索、按优先级筛选、按源静音。

### 16.4 扩展配置

- **模板市场**：一键装"每日天气播报""GitHub 提醒""HackerNews 摘要"；
- **表单模式**：调某源的间隔、关键词、免打扰；
- **自定义 MCP server**：填 URL + 令牌即接入，agent 立即多出新能力；
- **开发者模式**：App 内直接编辑连接器 YAML（带校验补全）；
- **逃生舱**（文档引导）：Node-RED sidecar、SSH、自挂 webhook。

### 16.5 维护与异常

- 系统页：状态监控、一键更新、备份导出/导入（加密配置包）；
- 换手机：登录即全量同步（数据全在服务器）；
- VPS 迁移：导出备份包 → 新机器装 → 导入；
- IM 授权过期（Telegram 等）：推送提醒 → App 内重新授权；
- 播报不响：诊断页一键自检（通知权限/白名单/三通道状态/推送自测），按机型给修复指引；
- 支持边界：官方托管版由运营方运维；自助版社区支持。

## 附录 B：CloudEvents 事件格式完整定义

```json
{
  "specversion": "1.0",
  "id": "uuid-v4",
  "source": "反向DNS风格源标识，如 wechat.group.pku-2026 / phone.notification / agent.pc-worker-1",
  "type": "点分层级，如 im.message.received / calendar.event.upcoming / agent.task.completed / user.command.spoken",
  "time": "RFC3339 时间戳",
  "subject": "人类可读的会话/线程名",
  "datacontenttype": "application/json",
  "data": {
    "actor": {"name": "发送者", "id": "源内 ID"},
    "title": "一句话标题",
    "body": "正文/摘要",
    "priority_hint": "high | normal | low | silent",
    "actions_available": [
      {"name": "reply", "via": "mcp:wechat-bot", "params": {"chat_id": "..."}},
      {"name": "add_to_calendar", "via": "mcp:google-calendar"},
      {"name": "mute_source", "via": "gateway-rule"}
    ],
    "refs": {"thread_id": "...", "url": "..."},
    "raw": { "源原始载荷，调试用": "..." }
  }
}
```

约定：

- `priority_hint` 只是源的暗示，最终优先级由核心 Agent 结合用户画像判定；
- `actions_available[].via` 指明动作执行通道：mcp server 名 / gateway-rule（Node-RED 直接做）/ a2a agent 名；
- 事件只追加不修改；敏感字段在网关侧脱敏后再入总线。
